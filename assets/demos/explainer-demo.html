notebook 双层捕获机制：hook × skill 如何协同

拆解 smart 插件里 notebook 功能如何用 hook + skill 两条通道共同维护 .smart/notebook.md：各自职责、协作协议与常见陷阱。

1 是什么、在哪

smart 插件里，notebook 是唯一同时用 hook 和 skill 两条通道实现的功能。它要解决的问题是：长对话中 Claude 抛出的洞见（★ Insight 块）和"建议下一步"经常被后续讨论淹没，用户回头想找的时候已经翻不到了。notebook 把这些未闭合线索持久化到 .smart/notebook.md，并追踪它们的 open / closed 状态。

它与另外两个持久化组件严格正交：

  • todo — 决策与主线，防止对话跑偏
  • distill — 知识问答对，供 RAG 检索
  • notebook（本页主角） — 只管还没处理完的未闭合线索

2 心智模型

一句话版本： 两条通道写同一份文件——Stop hook 在每次回复结束后自动扫描固定格式的标记块，零遗漏但认死格式；/smart:notebook skill 由用户显式调用，能读懂自由形式的线索、管理 open/closed 状态流转。二者靠内容指纹（<!-- h:... -->）去重协议共存：谁都不能整文件重写，只能先读全文再增量修改。

4 两层各自如何工作

层载体触发模型擅长
确定性层hooks/notebook-capture.py（Stop hook）每次 Claude 回复结束后自动运行无（纯 Python）抓取格式固定的标记块，零遗漏
语义层/smart:notebook skill用户显式调用sonnet识别自由形式的线索、管理状态流转

设计动机：不能指望 Claude 自觉记录。如果只有 skill 层，用户忘了调用，线索就丢了；如果只有 hook 层，非标记格式的线索（比如对话里随口提到的"这里以后要改"）抓不到。两层叠加才能既兜底又全面。

hook 层：Stop 事件触发

Stop 事件在 Claude 每次回复结束时触发，notebook-capture.py 收到的输入里包含本次回复的完整文本。处理流程：

  1. 解析标记块：用正则匹配 ★ Insight ─── 到 ─── 的围栏，以及"建议下一步 / Next steps"引导的列表段
  2. 生成指纹：对每条捕获内容计算短哈希，写成 HTML 注释 <!-- h:a1b2c3 --> 附在条目后
  3. 去重：读取现有 .smart/notebook.md，指纹已存在的条目跳过——同一个洞见在多轮回复里反复出现时只落一次盘
  4. 追加写入：新条目追加到 open 区，带捕获时间戳

hook 层从不做语义判断，也从不改动已有条目的状态——它只保证"标记块必然落盘"这一件事。

skill 层：用户显式调用

/smart:notebook（model: sonnet）做 hook 做不了的三件事：

  1. 自由形式捕获：通读当前对话，把没有 ★ 标记但明显是未闭合线索的内容（"回头看看那个内存泄漏"、"这个配置先硬编码，之后要抽出来"）提炼成条目
  2. 状态管理：把已经解决的线索移到 closed 区，合并语义重复的条目
  3. 汇报：按 open 时长排序输出当前未闭合线索，提醒用户最老的悬案

共享协议：读-改-写

两层共用 .smart/notebook.md（git-ignored 的个人草稿状态）。因为两个写入方互不知晓对方何时运行，协议是强制的：

硬约束： skill 层合并条目时必须保留 hook 层的 <!-- h:... --> 指纹——丢了指纹，hook 层下次就会把同一条洞见当新内容再写一遍，产生重复。
  • 任何一方写入前必须先读全文，在现有内容上增改，绝不整文件重写
  • hook 层只追加 open 区，绝不触碰 closed 区和 skill 层写的条目

5 边界与陷阱

指纹是唯一的去重依据： 手工编辑 notebook.md 时删掉了 <!-- h:... --> 注释，对应洞见会在下次回复后"复活"。
hook 解析依赖围栏格式： ★ Insight 块如果被输出样式改了围栏字符，正则会漏抓——改输出样式时要同步核对 notebook-capture.py 的正则。
两层时序无保证： skill 正在整理时 hook 可能又追加了新条目，所以 skill 的读-改-写窗口要尽量短，且只对读到的内容负责。
不是任务管理器： 闭合一条线索的标准是"这件事有了结论或不再重要"，不是"做完了"——做完与否归 todo 管。
