认证模块重构方案：从单体 Session 到 JWT + 刷新令牌

一句话：把当前的服务端 Session 认证升级为 JWT + 刷新令牌双轨过渡方案，用于本次架构评审的 go/no-go 决策。

1 结论与规模

结论： 认证体系从纯 Session 升级为 JWT + 刷新令牌双轨过渡（方案 B）。8 周内新登录全部切到 JWT，存量 Session 只读兼容至自然过期，网关本地验签、不再回源 auth-service。

背景与痛点

  • 移动端 App / 小程序与 Web 共用 Cookie-Session 机制，Cookie 在 iOS WKWebView 与部分安卓 ROM 上丢失率约 3.2%，导致用户被随机登出
  • Session 全量存 Redis，高峰期内存占用 78%，扩容一次需要停写迁移
  • 网关层无法独立校验身份，所有请求都要回源到 auth-service 查 Session，auth-service 成为全站单点；P99 延迟 45ms 中有 18ms 花在这次往返上
  • 第三方开放平台接入需要 OAuth2，现有架构无法复用任何组件，等于要再写一套

2 目标与非目标

目标
  • 网关层可本地校验身份，不回源 auth-service
  • 移动端登录态 30 天内无感续期，Cookie 依赖降为零
  • Redis 认证相关内存占用下降 80% 以上
  • 为后续 OAuth2 开放平台复用同一套令牌签发体系
非目标
  • 不做单点登录（SSO）跨主域打通，那是 Q4 的独立项目
  • 不迁移历史用户的密码哈希算法（bcrypt 保持不变）
  • 不引入第三方身份提供商（IdP），本次全部自建

3 方案设计

备选方案对比

方案 A · 全量切换 JWT，无状态化

登录签发 JWT（15 分钟）+ 刷新令牌（30 天），Session 机制一次性下线。

架构最干净，Redis 认证内存直接归零，网关本地验签
无法主动踢人（登出/封号要等 access token 自然过期）
一次性切换风险大，2100 万在线 Session 需强制全员重新登录，客服压力不可控
已选定

方案 B · 双轨过渡，JWT 优先

新登录一律走 JWT + 刷新令牌；存量 Session 保留只读兼容，网关先验 JWT，失败再回退 Session 校验。8 周后存量 Session 自然过期完毕，删除回退逻辑。

零强制登出
可灰度（按 App 版本放量）
回退逻辑清晰，有明确下线时间
过渡期需同时维护两套校验；网关多一次条件分支，预估增加 0.3ms

方案 C · 引入第三方 IdP（Auth0 / Keycloak）

OAuth2/OIDC 全家桶开箱即用
核心登录链路引入外部依赖，合规评审预计 6 周起步
按 MAU 计费，成本年增约 $8.4 万
与「非目标：不引入 IdP」直接冲突
决策： 选方案 B。方案 A 的强制登出代价业务侧不接受；方案 C 被成本与合规否决。

令牌设计

令牌载体有效期存储
Access Token（JWT，RS256）Authorization 头15 分钟客户端内存
Refresh Token（不透明串）httpOnly Cookie（Web）/ Keychain（App）30 天，滑动Redis rt:*，仅存哈希
  • JWT payload：sub（用户 ID）、sid（会话族 ID，用于踢人）、scope、iat/exp，不放任何 PII
  • 公钥通过 /.well-known/jwks.json 暴露，网关每 10 分钟拉取缓存；密钥对每 90 天轮换，JWKS 同时保留新旧两把公钥
  • 踢人方案：封号/改密时把 sid 写入 Redis 黑名单（TTL = access token 剩余寿命上限 15 分钟），网关验签后查黑名单——黑名单预计常态 < 1 万条，内存可忽略

接口变更清单

接口变更兼容性
POST /login响应增加 access_token / refresh_token 字段向后兼容，保留 Set-Cookie
POST /token/refresh新增—
POST /logout追加吊销 refresh token 与 sid 拉黑向后兼容

4 架构与数据流

  • auth-service 提供 /login、/logout、/verify 三个接口
  • Session TTL 7 天，滑动续期，每次请求都会 EXPIRE
  • Redis 中 session key 约 2100 万个，平均 1.4KB
网关中间件伪代码（Go） 
func AuthMiddleware(c *gin.Context) {
    token := extractBearer(c)
    if token != "" {
        claims, err := verifyJWT(token, jwksCache)
        if err == nil && !sidBlacklisted(claims.Sid) {
            c.Set("uid", claims.Sub)
            c.Next()
            return
        }
        metrics.Incr("auth.jwt.fallback") // R3: 回退必须可观测
    }
    // 过渡期回退：存量 Session 校验，8 周后整段删除
    if uid, ok := legacySessionVerify(c); ok {
        c.Set("uid", uid)
        c.Next()
        return
    }
    c.AbortWithStatus(401)
}

5 风险清单

#风险等级影响缓解
R1密钥泄漏导致任意伪造身份高全站私钥入 KMS，签发服务独立部署，90 天强制轮换；泄漏应急预案：立即轮换 + 全量 sid 拉黑
R2刷新令牌被窃取后长期冒用高单用户刷新令牌旋转（每次刷新作废旧 token），检测到旧 token 复用即吊销整个会话族
R3双轨期回退逻辑掩盖 JWT 故障中可观测性回退命中率上报监控，> 5% 告警；灰度期每日核对两轨校验结果抽样
R4时钟偏移导致验签误拒中零星请求验签容忍 ±60s；网关 NTP 巡检纳入部署检查项
R5JWKS 拉取失败导致网关不能验签中全站公钥本地缓存 24h 兜底 + 双源拉取；缓存失效且拉取失败时降级回 Session 轨
R6移动端旧版本长期不升级低长尾用户Session 轨保底 8 周；期满后旧版本强制升级弹窗

6 里程碑

  1. M1（第 1–2 周）：签发侧就绪
    • JWT 签发模块 + KMS 集成 + JWKS 端点
    • refresh token 存储（哈希落 Redis）与旋转逻辑
    • 单元测试覆盖签发/刷新/吊销全路径
  2. M2（第 3–4 周）：校验侧就绪
    • 网关 JWT 验签中间件（含黑名单查询、回退 Session）
    • 回退命中率、验签失败率监控面板与告警
    • 压测：网关本地验签 P99 增量 < 0.5ms
  3. M3（第 5–6 周）：客户端接入与灰度
    • Web / iOS / Android 三端 SDK 改造
    • 按 App 版本灰度：5% → 30% → 100%，每档观察 48h
    • 客服话术与 FAQ 同步
  4. M4（第 7–14 周）：过渡期收尾
    • 存量 Session 自然过期监控（预计第 13 周归零）
    • 下线 /verify 与网关回退逻辑
    • Redis session:* 键空间清理，回收内存并出对比报告

7 未决问题

Q1 · 刷新令牌的多设备策略： 同一账号是否限制刷新令牌数量上限（草案：10 个，LRU 淘汰）？超限踢最旧设备还是拒绝新登录？——需要产品侧本周内拍板
Q2 · 网关黑名单查询的降级语义： Redis 黑名单查询超时时，是放行（可用性优先）还是拒绝（安全优先）？安全团队意见与 SRE 相左，需要架构评审会裁决
Q3 · 开放平台的 scope 粒度： 本次只预留 scope 字段还是直接定义首批 scope 枚举？影响 JWT payload 是否稳定

8 验收标准

  • 网关认证相关回源 QPS < 1000（现 4.2 万）
  • Redis 认证内存占用下降 ≥ 80%
  • 移动端周登出投诉工单下降 ≥ 90%
  • 封号后 15 分钟内全端失效，实测通过
  • 密钥轮换演练一次通过，JWKS 新旧共存期无验签失败
  • 回退逻辑下线后连续两周无认证类 P0/P1
