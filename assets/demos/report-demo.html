3 核心论点

超过 100 行的 Markdown 基本没人读完；HTML 有布局、颜色、SVG、折叠、页内导航，本质是把 Agent 交付物从"文档"升级为"临时的任务专用界面"。这是三位信源共同的立论基础，也是"输出上限解除后 token 成本不再是硬约束"这一前提变化的直接后果。

5 反对声音：四条质疑

质疑点说明影响程度
Git diff 困难 HTML 源文件难以 git diff，审查噪音大。 中
Token 成本更高 生成 HTML 比生成 Markdown 更贵，作者自己也承认这一点。 低
脚本安全风险 一旦含 JavaScript，打开文档等于运行 Agent 生成的代码，存在 XSS、外部资源加载、数据泄漏风险。 高
双重事实源 md 与 html 并存易形成双重事实来源，内容漂移。 高

6 结论：三层交付模型

把上述正反两方论点收敛成一条可落地的规则——按"谁是事实、谁是视图"分层，而不是二选一：

层级角色版本控制说明
代码 + 测试 真正交付（Delivery） 进版本控制 唯一可运行、可验证的产出。
Markdown / Spec 长期事实（Source） 进版本控制 团队协作与长期维护的依据。
HTML 人类审阅层（View） 不进版本控制，从源派生 一次性生成、不反向维护，不得替代 spec。

落地规则

  • 自包含单文件（无外部依赖）
  • 默认零 JavaScript
  • 禁 CDN 与远程资源加载
  • 页脚标注 commit SHA 与生成时间
  • HTML 不得替代 spec
