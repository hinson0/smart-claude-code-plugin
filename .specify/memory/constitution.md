# Smart 双宿主插件宪法

## 核心原则

### I. 双宿主一致性
每项受支持的能力都必须保持仓库的双宿主结构。Codex 集成必须使用
`.agents/plugins/marketplace.json` 和 `plugins/smart/.codex-plugin/plugin.json`；Claude Code
集成必须使用 `.claude-plugin/marketplace.json` 和
`plugins/smart/.claude-plugin/plugin.json`。两份插件清单必须使用完全相同的干净语义化
版本，不得添加宿主专用的构建元数据。任一宿主缺少所需制品或制品过期时，变更均不算
完成。这样可以确保两个已声明支持的宿主都能正常安装，并保持行为一致。

### II. 用户文档同步
任何功能变更、组件增删或用户可见行为改动，都必须在同一次变更中更新 `README.md`、
`README_CN.md`、`README_TW.md`、`README_KO.md` 和 `README_JA.md`。所有语言版本必须描述
相同的命令、边界、前置条件和行为。仅修正文案且不改变含义时，可以只修改受影响的
翻译。这可防止使用不同语言的用户收到相互冲突的产品约定。

### III. 中英文源文件配对
除名为 `CN.md` 或 `CN[<名称>].md` 的翻译文件外，`plugins/` 下由宿主加载的文件、
可执行消息和代码注释必须使用英文。每个 `SKILL.md` 必须有同目录的 `CN.md`；每个英文
skill 参考文件必须有对应的 `CN[<名称>].md`。修改英文 skill 或参考文件时，必须在同一
次变更中更新对应的中文文件。这样既能保持运行时语言稳定，又能确保中文文档完整且
持续维护。

### IV. 自动化范围与安全
每个 skill 只能执行其契约声明的操作，不得自行推导运行无关 CI、升级版本、push、
merge、创建 PR 或 MR、修改标签或变更 Issue 的权限。影响远程系统的写操作必须获得
用户明确授权。只读诊断必须区分已验证事实与缺失证据；当目标或权限存在歧义时，破坏性
或不可逆操作必须安全失败。这样可以确保自动化工作流可审计，并防止狭窄请求在不知情的
情况下扩大影响范围。

### V. 版本化且经过验证的交付
插件行为发生变化时，必须将两份宿主清单更新为完全相同的干净 SemVer，并加入覆盖变更
契约的测试或确定性验证。维护者必须运行相关仓库检查，包括清单验证、skill 与翻译配对
检查、运行时语言检查和针对性行为测试。任何必需检查失败或尚未运行时，都不得声称发布
已经完成；无法执行的检查必须明确报告。这样可以确保版本号代表两个宿主上相互匹配且
经过验证的制品。

## 仓库约束

- Conventional Commit 消息必须使用 `<type>(<scope>): <description>`，总长不得超过 72
  个字符；除非项目级指令规定了更严格的范围，否则 type 只能是 `feat`、`fix`、
  `refactor`、`docs`、`test`、`chore`、`perf` 或 `ci`。
- 提交自动化必须按语义目的分组，将提交 type 视为硬边界，并将无关目的拆分为不同提交。
  提交流程不得运行 CI、升级版本或执行远程操作。
- 组件必须保留在已记录的双宿主目录结构中。已废弃的截图和运行时制品不得继续作为具有
  误导性的有效资产留在仓库中。
- 项目级 `AGENTS.md`、`CLAUDE.md` 和 `CLAUDE.local.md` 可以增加更严格的操作规则，
  但不得削弱本宪法。

## 开发流程与质量门禁

1. 先修改组件的英文源文件，再更新其中文翻译；适用原则 II 时，还必须同步更新五份用户
   README 文件。
2. 行为发生变化时，必须同时更新两份宿主清单，并保持完全相同的干净 SemVer。
3. 运行针对性行为测试，以及适用的清单、配对关系和运行时语言检查。
4. 发布或交接前，检查最终差异中的宿主一致性、范围边界、文档一致性，以及每项必需检查
   的证据。

评审必须指出适用的宪法原则，并拒绝违反“必须”规则的变更。任何例外都需要修订宪法；
仅凭实现说明或评审批准不能豁免原则。

## 治理

本宪法是项目最高级别的仓库治理文件。修订必须以对本文件的明确编辑提出，说明原因和
迁移影响，更新同步影响报告，并在依赖工作采用修订内容前获得维护者批准。操作指令可以
更严格，但不能覆盖宪法中的“必须”规则。

版本遵循语义化版本规则：删除原则或对原则作不兼容的重新定义时升级 MAJOR；新增原则或
实质扩展治理要求时升级 MINOR；仅作不改变语义的澄清时升级 PATCH。批准日期始终保留
首次采纳日期；治理含义或文字发生任何变化时，最后修订日期都必须更新。

每份规格、计划、任务清单、实现评审和发布交接都必须检查所有适用原则的合规性。评审者
必须在批准前记录违规项、失败的检查和未经验证的声明。复杂性或例外必须通过修订提案
说明理由，不得被默认接受。
