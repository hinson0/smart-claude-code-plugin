# Smart 双宿主插件宪法

## 核心原则

### I. 多插件双宿主一致性
仓库可以发布多个相互独立的插件，但每个插件都必须完整支持 Codex 与 Claude Code。根级
`.agents/plugins/marketplace.json` 和 `.claude-plugin/marketplace.json` 必须登记相同的
插件集合，并分别指向同一个 `plugins/<插件名>` 目录。每个插件目录必须同时包含
`.codex-plugin/plugin.json` 和 `.claude-plugin/plugin.json`；两份 manifest 的插件名称必须
一致，版本必须是完全相同的干净 SemVer。不同插件可以使用互不绑定的版本。任一根级
marketplace 集合不一致，或任一插件缺少宿主制品时，相关变更均不算完成。这样既能保证
两个宿主获得相同的插件目录，也能保持插件之间的安装、命名空间和版本边界。

### II. 用户文档同步
任何插件的功能变更、组件增删、安装入口调整或用户可见行为改动，都必须在同一次变更中
更新 `README.md`、`README_CN.md`、`README_TW.md`、`README_KO.md` 和 `README_JA.md`。
所有语言版本必须描述相同的插件集合、安装来源、命令、命名空间、边界、前置条件和行为。
仅修正文案且不改变含义时，可以只修改受影响的翻译。这可防止不同语言或不同宿主的用户
获得相互冲突的 marketplace 与插件约定。

### III. 中英文源文件配对
本原则适用于 `plugins/` 下的每个插件。除名为 `CN.md` 或 `CN[<名称>].md` 的翻译文件外，
由宿主加载的文件、可执行消息和代码注释必须使用英文。每个 `SKILL.md` 必须有同目录的
`CN.md`；每个英文 skill 参考文件必须有对应的 `CN[<名称>].md`。修改英文 skill 或参考
文件时，必须在同一次变更中更新对应的中文文件。必须保留的非英文协议值可以存在，但其
用途必须由测试证明，且不得借此放宽其他运行源的英文边界。这样既能保持运行时语言稳定，
又能确保每个插件的中文文档完整且持续维护。

### IV. 自动化范围与安全
每个 skill 只能执行其契约声明的操作，不得自行推导运行无关 CI、升级版本、push、
merge、创建 PR 或 MR、修改标签或变更 Issue 的权限。影响远程系统的写操作必须获得
用户明确授权。只读诊断必须区分已验证事实与缺失证据；当目标或权限存在歧义时，破坏性
或不可逆操作必须安全失败。这样可以确保自动化工作流可审计，并防止狭窄请求在不知情的
情况下扩大影响范围。

### V. 独立版本化且经过验证的交付
任一插件行为发生变化时，只能升级该插件自己的两份宿主 manifest，并保持两者使用完全
相同的干净 SemVer；不得因同仓库内另一个插件变化而制造无内容版本。新增插件必须拥有
自己的初始版本，删除或迁移插件必须保留可审计的版本和回退证据。维护者必须为实际变化
的插件运行相关检查，包括 manifest 验证、skill 与翻译配对、运行时语言检查和针对性行为
测试；添加或删除插件时还必须验证两个根级 marketplace 的插件集合一致。任何必需检查
失败或尚未运行时，都不得声称相应插件或仓库发布已经完成；无法执行的检查必须明确报告。
这样可以确保每个版本只代表对应插件上经过验证的制品，并避免无关插件相互污染发布记录。

## 仓库约束

- Conventional Commit 消息必须使用 `<type>(<scope>): <description>`，总长不得超过 72
  个字符；除非项目级指令规定了更严格的范围，否则 type 只能是 `feat`、`fix`、
  `refactor`、`docs`、`test`、`chore`、`perf` 或 `ci`。
- 提交自动化必须按语义目的分组，将提交 type 视为硬边界，并将无关目的拆分为不同提交。
  提交流程不得运行 CI、升级版本或执行远程操作。
- 每个发布插件必须位于独立的 `plugins/<插件名>` 目录；插件 payload、hook、状态和测试
  合同不得因目录便利而隐式并入另一个插件。共享仓库文件必须明确其适用插件范围。
- 组件必须保留在已记录的双宿主目录结构中。已废弃的截图和运行时制品不得继续作为具有
  误导性的有效资产留在仓库中。
- 项目级 `AGENTS.md`、`CLAUDE.md` 和 `CLAUDE.local.md` 可以增加更严格的操作规则，
  但不得削弱本宪法。

## 开发流程与质量门禁

1. 先识别本次变更影响的插件和仓库级文件，再修改各插件的英文源文件并同步中文翻译。
2. 新增、删除或迁移插件时，必须同步更新两个根级 marketplace，并验证插件名称、source
   path 和插件集合一致。
3. 插件行为发生变化时，只更新实际变化插件的两份 manifest，并保持该插件版本完全一致；
   未发生 payload 变化的其他插件不得被动升级。
4. 适用原则 II 时，必须同步更新五份用户 README，明确各插件的独立安装、命名空间、依赖、
   迁移与回退边界。
5. 对每个受影响插件运行针对性行为测试，以及适用的 manifest、配对关系、运行时语言和
   双宿主发现检查。
6. 发布或交接前，检查最终差异中的插件边界、宿主一致性、版本范围、文档一致性和每项
   必需检查的证据。

评审必须指出适用的宪法原则，并拒绝违反“必须”规则的变更。任何例外都需要修订宪法；
仅凭实现说明或评审批准不能豁免原则。

## 治理

本宪法是项目最高级别的仓库治理文件。修订必须以对本文件的明确编辑提出，说明原因和
迁移影响，更新同步影响报告，并在依赖工作采用修订内容前获得维护者批准。操作指令可以
更严格，但不能覆盖宪法中的“必须”规则。

版本遵循语义化版本规则：删除原则或对原则作不兼容的重新定义时升级 MAJOR；新增原则或
实质扩展治理要求时升级 MINOR；仅作不改变语义的澄清时升级 PATCH。批准日期始终保留
首次采纳日期；治理含义或文字发生任何变化时，最后修订日期都必须更新。

每份规格、计划、任务清单、实现评审和发布交接都必须检查所有适用原则的合规性。评审者
必须在批准前记录违规项、失败的检查和未经验证的声明。复杂性或例外必须通过修订提案
说明理由，不得被默认接受。
